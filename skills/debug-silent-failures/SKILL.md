# 排查「静默失败」

## 什么时候用

中了任意一条就适用：

- 命令**正常结束**，但输出文件是空的（0 字节或只有一个换行）
- 输出行数**比输入少**（跑了 20 条，结果只有 19 条）
- 指标算出来是 **0%** 或明显不合理
- 跑得**异常快**（本该几分钟，几秒就"完成"了）
- 屏幕上**一个报错都没有**

**根因几乎总是同一个**：代码用 `except Exception: pass` 或 `except: continue` 把错误吞掉了。

## 核心原则

> **先找到那个 `except`，然后绕过它。**

不绕过它，你永远只能看到"结果是空的"，看不到"为什么空"。

## 步骤

### 1. 先数数量，别看内容

```bash
wc -l 输入文件 输出文件
```

**行数对不上就停下**——不要继续算指标，先把丢的那些找出来。

### 2. 找到"吞错"的位置

```bash
grep -rn 'except' --include=*.py . | grep -v raise
```

| 写法 | 后果 |
|---|---|
| `except Exception: pass` | 完全无声 |
| `except Exception as e: continue` | 循环里静默跳过这一条 |
| `except X as e: print(...)` | 至少留了痕（可接受） |

### 3. 绕过它，直接调底层函数 ← 最关键

写个十来行的小脚本，直接调那个被 `try` 包住的函数，让异常抛出来：

```python
rows = [json.loads(l) for l in open("输入文件")]
for i, r in enumerate(rows):
    try:
        out = 被吞掉的那个函数(r)
        print("[%2d] OK" % i)
    except Exception as e:
        print("[%2d] ❌ %s: %s" % (i, type(e).__name__, str(e)[:150]))
        traceback.print_exc()      # 第一个失败的完整堆栈
```

### 4. 按根因分类处理

| 根因 | 处理 |
|---|---|
| 异常类型**不在重试列表**里 | 加进重试列表（最省事） |
| 返回值**没判空** | `if x is None: raise ValueError(...)`——变成**可重试**的错误 |
| 外部服务偶发失败（网络、上游拒绝） | 让异常可重试；跑之前先做一次连通性检查 |
| 循环里 `continue` 静默跳过 | 改成累计失败计数，最后一起打印 |

### 5. 加检查点，防止再犯

每个环节后面加一条**能失败的检查**：

```bash
wc -l 输出文件          # 数量对不对
test -s 输出文件        # 非空
grep -c 报错关键字 日志 # 0 次
```

## 检查点：怎么确认修好了

| 检查 | 期望 |
|---|---|
| 重跑后数行数 | **和输入一样多** |
| 日志里的报错计数 | 0（或有重试记录但最终成功） |
| 输出文件大小 | 不是 0 字节 |
| 运行时长 | **合理**（还是几秒 = 根本没发出请求） |

## 常见失败与处理

| 现象 | 处理 |
|---|---|
| 几秒"完成"了几十条 | 请求根本没发出去——查网络和认证 |
| `AuthenticationError` / `No API key` | 环境变量没生效：`source ~/.bashrc` 或重开终端 |
| 输出 0 字节、日志也没报错 | 异常类型不在重试列表 → 按第 4 步分类 |
| 每次都失败但计数正常 | 看循环体的 `except` 是不是 `pass` |

## 不要做什么

- **不要**一看"结果是空的"就去放大参数（token、timeout）——那是绕过现象
- **不要**在定位到根因之前就加 `try/except`——问题会被埋得更深
- **不要**只看最后一行报错——静默失败**没有**报错，要自己造检查点
- **不要**把"改完能跑了"当成"修好了"——要能说清原来为什么失败
